# A 项目后台双模式登录

用户要求将 B 的密码 / Git Token 二选一登录应用到 A，并同步 A 的 README；确认可行后直接实施。

## 方案

采用 B 的浏览器端加密机制，接入 A 的现有后台和 Git API。只复制登录界面无法让静态网站保存密码；整体搬入 B 的 Git 服务则会替换 A 已有的数据、图床和自有部署流程。复用原生 Web Crypto 和 A 的请求实例，是改动最小的完整方案。

## 行为与边界

- 后台仍为 `/system`。未设置凭证时使用 Token；有效凭证默认密码登录，并保留 Token 兜底。自有服务器继续验证服务器密码。
- 站点设置增加独立密码管理：设置、修改、确认移除；密码至少 8 个字符且包含字母和数字，推荐 12 位以上独有口令。
- `data/auth.json` 使用独立 `nav-auth` v1 格式，PBKDF2-SHA-256 600,000 次、AES-256-GCM，随机 salt / IV，绑定实际主仓库、图床及分支。密文内包含主 Token 和需要时的独立图床 Token。
- 两种入口统一验证 Git 用户和目标仓库写权限；全部校验成功才保存当前标签页会话。迁移清除旧 localStorage 凭证，不自动迁移明文 Token。
- 凭证单独提交并携带读取版本；冲突保留输入并要求重新读取。保存后等待部署完成。
- 构建严格验证凭证，单独发布到 `data/auth.json`，空白 / 移除时清理旧资源。读取禁用缓存并绕过 PWA 缓存；网络或 HTML 回退错误保留 Token 登录。
- 不引入服务器账号、注册、多用户、博客功能或新依赖。公开密文可被离线猜解；换密码不能撤销旧 Token。

## 修改范围

登录组件、共享 Token 校验及其启动校验调用、会话存储、密码管理组件 / 服务、单文件凭证 Git API、初始化与静态资源配置、缓存头、中文 / 英文 README 和新增认证测试。A 无 Git 元数据，在用户指定目录原位修改并保留外部备份；B 只读。
